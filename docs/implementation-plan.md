# 사내 AI Agent Harness 구현 계획 초안

이 문서는 초기 단계 구분과 전체 수용 기준을 보존한다. 실제 진행 상황과 다음 작업은 [progress.md](progress.md)를 우선 참고한다. 아래 GPUI는 초기 검증 후보이며 현재 개발 빌드는 Rust eframe/egui를 사용한다. 이미 구현된 설정·모델 endpoint·RPC도 있으므로 아래의 '남은 결정' 전체가 현재 미결인 것은 아니다.

개발은 기술 검증, 실행 기반, 편집 환경, 업무 맥락, 결과 연결, 자기 개선 경험 순으로 진행한다. 중간 빌드는 시험용으로 사용한다. 사용자가 요청한 첫 사용 가능한 버전의 범위를 단계 구분만으로 축소하지 않는다. 일정은 기술 검증 결과와 실제 사내 접근 가능 범위를 확인한 후 산정한다.

## 단계별 작업과 완료 기준

| 단계 | 핵심 작업 | 완료 기준 |
| --- | --- | --- |
| 0 기술 검증 | GPUI 한글 입력·편집·터미널, Cordis core 전환, 장기 작업 유지, SSH·Docker·Office | 각 검증에 재현 가능한 절차와 실패 조건, 채택·수정 결정을 남김 |
| 1 실행 기반 | 기록·세션·승인·자원·스케줄링·모델 어댑터·로컬과 원격 실행 | 재연결·재개 시 기록과 실제 상태가 일치하고 불명확한 외부 실행을 중복 수행하지 않음 |
| 2 개발 작업공간 | 편집·LSP 패키지·Git·worktree·원격·Docker·언어별 설정 | 모든 지정 언어의 합의한 기능을 대표 프로젝트에서 검증 |
| 3 업무 맥락 | Outlook·웹·메신저·첨부·SQLite·키워드 검색·EmbeddingGemma 2·기억·공유 자산 | 결과와 결정에서 원문·버전·프로젝트 근거를 추적 가능 |
| 4 결과 연결 | Office·wiki·웹 초안·Confluence·PR·Linux ADB·NPU 어댑터와 사내 프로그램 등록·GPU dummy | 조사→개발·실험→검토→산출물의 대표 흐름을 실행 |
| 5 자기 개선 경험 | 제안·동의·후보 환경·적용·평가·복원 UI | 명시적 개선 요청 1건을 전체 절차로 수행하고 사용자 평가 기록 |

Core 교체의 기술 검증은 0단계, 실제 사용자 흐름은 5단계에 있다. 기능 개발 중에도 hot reload·상태 호환성 기준을 계속 적용한다.

## 먼저 수행할 기술 검증

1. Windows 한글 조합·붙여넣기·선택·undo·배율 변경·분할 편집을 GPUI 후보에서 검증하고 Linux 빌드도 확인한다.
2. 독립된 장기 작업을 실행한 상태에서 agent loop 제공자를 교체하고 로그·작업 ID·대화·대기 입력이 유지되는지 확인한다.
3. 구버전과 신버전의 공존, 후보 초기화 실패, 늦게 도착한 결과, 상태 형식 불일치, 안전 지점 대기 시간 초과를 시험한다.
4. SSH config와 jump host를 이용해 파일·명령·LSP를 연결하고, 연결을 끊은 뒤 관리 작업을 재조회한다.
5. Docker 호스트 마운트·컨테이너 경로·Git worktree를 연결하고 실제 편집 대상과 빌드 대상을 비교한다.
6. 사내 환경에서 DRM Office의 읽기·기존 파일 수정·저장·복구·미리보기를 확인한다. 사내 환경을 사용할 수 없다면 미검증 상태를 유지한다.
7. 대표 Android 다중 모듈 프로젝트의 Gradle·AGP·JDK·SDK 조건과 Kotlin·Java 탐색·진단을 검증한다.
8. 자체 Chrome 확장프로그램·Native Messaging 연결을 검증하고 기존 인증 세션, 전용 환경의 SSO, 메신저 UI 요소 접근 가능성을 확인한다.
9. Linux에 USB로 연결된 기기의 조회·배포·실행을 검증하고, 각 NPU SDK의 실제 입력·변환·평가 계약을 대표 모델로 확인한다.
10. 로컬 EmbeddingGemma 2의 텍스트·코드·이미지 768차원 검색, 한국어 검색과 질의·문서 설정 호환성을 검증한다. CPU·GPU 자원 사용, 사용자 검색 우선 처리·색인 재개, 임베딩 장애 시 키워드 검색 유지도 시험한다.

GPU pool은 합의대로 dummy를 만든다. NPU 변환·평가 프로그램은 현재 사내에서만 접근 가능하므로 등록 기능과 fixture로 공통 실행 계약을 먼저 검증하고 실제 SDK 통합은 사내 연결 후 검증한다. 다른 사내 연동도 mock 결과를 실제 통합 완료로 표시하지 않는다.

## 편집 지원 완료 기준

모든 지정 언어에 파일 열기·저장·분할·구문 강조·자동완성·정의 및 참조 탐색·진단을 검증한다. 문법별로 적용되지 않는 기능은 계약에 명시하고 조용히 생략하지 않는다.

| 환경 | 추가 검증 |
| --- | --- |
| Python | uv 환경·설치된 의존성·PyTorch import와 진단 |
| C/C++ | NDK arm64-v8a toolchain, include·매크로·compile_commands, CMake 빌드 위치 |
| CMake | 프로젝트 구성·스크립트 편집·관련 진단과 실행 명령 |
| TypeScript | 프로젝트 설정·모듈 해석·타입 진단 |
| Rust | toolchain·rust-src·workspace·Cargo 실행과 진단 |
| Kotlin와 Java | 혼용·다중 모듈·Android 의존성·정의 참조·빌드 진단 |
| Gradle Groovy | wrapper 버전·AGP 구분·스크립트 편집·동기화와 빌드 결과 |

자체 IDE의 첫 버전은 Android Studio의 모든 기능을 복제하는 것으로 정의하지 않는다. 사용자가 합의한 편집 기능을 실제 환경에서 충족하는 것을 기준으로 한다.

## 대표 업무 검증

- 관련 메일·Confluence에서 요구사항을 찾고 근거를 표시해 개발 작업을 생성한다.
- 선택한 개발 환경에서 NDK 코드를 수정·빌드하고 결과를 Linux USB 연결 기기에 배포해 로그·평가 결과를 작업에 연결한다.
- PyTorch QAT와 원본 ONNX export를 세 SDK의 Docker 변환·Linux USB 실기기 평가에 연결한다. SDK별 레이어 수정본을 별도 버전으로 관리하고 최종 출력 비교는 원본 ONNX를 기준으로 한다.
- 에이전트에게 사내 변환 스크립트·기존 평가 프로그램 등록을 요청하고, 설정 제안·동의·시험 실행·결과 파싱·활성화 흐름을 검증한다. 실제 프로그램과 검증 모델에 연결한 뒤 SDK별 통합 완료를 판정한다.
- SSH 또는 Docker에서 Python 프로젝트를 수정·검증하고 장기 학습 작업을 추적한다.
- GPU dummy로 제출·진행·실패·취소·재조회·파일 전송을 시험한다. 실제 CLI로 교체할 어댑터 계약을 남긴다.
- 모델 버전을 여러 프로젝트에서 참조하고 한 프로젝트의 변경이 다른 프로젝트의 선택 버전을 바꾸지 않는지 확인한다.
- 실험 결과를 Obsidian 새 노트, 회사 레이아웃 PowerPoint 초안, 웹메일 초안으로 연결한다.
- Confluence 게시 승인, PR 생성, 메신저 초안의 서로 다른 완료 지점을 검증한다.
- 명시적 자기 개선 요청을 승인·적용하고 사용자 평가가 없으면 평가 미정으로 유지한다.
- 과거 메시지 편집·분기 후 현재 작업공간에서 실행하고, 원본 대화와 과거 결과의 출처가 보존되는지 확인한다. 과거 코드 복원은 첫 버전 완료 기준에서 제외한다.

## 장애와 복구 검증

- GUI 종료와 재접속, 감독 프로세스 장애, 모델 스트림 단절, SSH 단절, 컨테이너 중지와 서버 재부팅을 다른 장애로 취급한다.
- 문서 저장·PR·workload 생성 직후 응답 유실 상황에서 결과 조회 없이 같은 행동을 반복하지 않는다.
- 50GB 근접·초과 시 원본 삭제 없이 캐시 정리와 수집 보류가 동작하는지 확인한다.
- 사용자의 미저장 코드, 외부 파일 수정, 두 agent의 같은 파일 수정 충돌을 검증한다.
- 원격 파일 경로·마운트 변경 시 잘못된 대상에 쓰지 않도록 확인한다.
- 구버전 승인이 바뀐 도구·인자·대상에 재사용되지 않는지 확인한다.
- 모델 전송 범위 설정이 수집 원문·첨부·기억·하위 agent에도 적용되는지 확인한다.
- USB 단절·기기 교체·동일 기기 동시 평가와 SDK 변환 실패 시 입력·결과·기기 소유권을 확인한다.
- 원본·파생 ONNX의 버전 및 평가 기준 혼동, 입력·출력 대응 불일치, 측정 불가 지표, 결과 파싱 실패를 검증한다.
- 수동 내보내기·가져오기 시 원본 포함 옵션, 원격 자산 참조, 기록 간 연결과 버전 호환성을 검증한다.
- SQLite 기록과 파일 저장소 사이의 부분 실패, 검색 색인 버전 불일치·재생성, 자격증명 경로 누락과 설정 재연결을 검증한다.
- YAML 설정의 계층·출처·UI 편집·직접 편집·검증 실패 후 기존 설정 유지를 확인한다.
- Chrome 탭 종료·페이지 이동·확장 또는 브리지 재시작·인증 만료·사용자 제어 회수 후 대상과 실행 결과를 재확인한다.
- Chrome 종료 시 정기 수집 보류, 인증 알림 중복 억제와 로그인 후 재개, 등록 범위 밖 탐색 제한, 조회 탭 정리와 초안·인계·고정·인증 탭 유지를 검증한다.

## 성능과 운영 검증

64GB PC에서 프로젝트 5개와 agent 10개를 기준으로 UI 응답, 메모리, LSP·검색 색인·빌드의 자원 경합을 측정한다. 모델 동시 요청 기본값은 3개다. 정확한 지연·메모리 목표는 초기 측정 후 정한다.

Node.js·Python 미포함 환경의 설치 진단, 사내 mirror·registry·CA와 인증 없는 proxy, 오프라인 언어 서버 패키지, 수동 업데이트·이전 버전 복원을 시험한다. 기존 네트워크 설정 재사용이 기본이며 자체 제작 실행 파일 사용은 가능하다. 자격증명은 설정의 파일 경로로 지정하고 운영체제 credential API는 사용하지 않는다. 관리자 권한 요구는 아직 미확인이다.

## 남은 결정

- FTS5 한국어 검색 구성·벡터 저장 구현, EmbeddingGemma 2의 고정 revision·장치별 실행 설정·배포 경로, 구체적인 생성 모델 endpoint.
- 대화·실행 기록 보관 기간과 수동 내보내기 형식. 50GB 원본 자료 영역과 구분.
- 자격증명 파일 경로 설정의 형식·내보내기 동작, SSH 키·브라우저 인증 상태의 재사용 경계.
- Windows 설치 권한과 사내 네트워크 설정의 구체적인 배포 경로.
- 사내 연결 후 확인할 NPU SDK 버전·Docker 이미지·기존 스크립트와 평가 프로그램 계약, ONNX 부가 자료·평가 preset·실제 검증 기기.
- 확정한 Chrome 확장프로그램·Native Messaging 구조의 사내 호환성, 브라우저 작업 진행 표시, 앱 내부 문서 미리보기의 DRM 환경 동작.
- 자기 개선 제안의 표시 형식과 범위 변경 판정. 명시한 수정·검증·적용은 한 번의 동의로 진행한다.
- MCP 연결 방식·설정·인증, skills의 적용 규칙과 프로젝트 preset 형식.
- 릴리스 범위의 기능별 검증 완료 여부와 사내 환경에서 남은 검증 항목.

## 개발 산출물 제안

제품 명세, 프로세스·플러그인·데이터 계약, 모델·도구 적합성 테스트, 기술 검증 보고, UI 흐름, 언어 지원 매트릭스, 로컬·SSH·Docker 시나리오, 설치·복구 안내를 유지한다. 구현 저장소의 실제 패키지 디렉토리 배치는 기술 검증 후 결정한다.
