# 사내 AI Agent Harness 구조 초안

[합의한 요구사항](requirements.md)을 구현하기 위한 설계 기준이다. 현재 구현·실제 검증·미완료 항목은 [검증 현황](validation.md)에 구분한다. Rust UI는 초기 GPUI 후보 대신 eframe으로 첫 개발 빌드를 검증했으며, 아래의 장기 설계 전체가 구현되었다고 해석하지 않는다.

## 실행 경계

| 구성 | 소유하는 상태와 책임 | 교체 방식 |
| --- | --- | --- |
| Rust Desktop | 편집 버퍼·배치·표시·사용자 상호작용 | 앱 업데이트와 재시작 |
| 상주 감독 프로세스 | 실행 버전·작업 소유권·프로세스 연결·장기 실행 핸들 | 상태를 기록한 재시작 |
| Cordis 실행 버전 | agent loop·모델 어댑터·도구·정책·context 전략 | 플러그인 교체 또는 실행 버전 전환 |
| 실행 서비스 | 명령·파일·PTY·Git·LSP·브라우저·기기 작업 | 작업별 drain과 재접속 계약 |
| Windows worker | Outlook·Office COM 세션과 작업 | 진행 상태를 확인한 worker 재시작 |
| 원격 실행부 | 원격 작업 ID·프로세스·로그·파일·컨테이너 연결 | SSH 재접속과 작업별 복구 |
| 저장 서비스 | durable 기록·원본 참조·상태 스냅샷 | 형식 버전과 호환성 기반 변경 |

상주 프로세스는 앱 기능을 집중시키는 거대한 고정 core가 되지 않게 한다. 프로세스 수명·실행 식별·원자적인 소유권 이전·기록 순서처럼 교체를 가능하게 하는 최소 기능에 한정하고, 업무 판단과 정책 구현은 플러그인에 둔다.

GUI는 표시용 이벤트만 믿고 작업 완료를 판단하지 않는다. 재연결 시 기록된 작업 상태와 이벤트 커서를 기준으로 복구한다. 통신 방식은 로컬 IPC 후보를 비교한 뒤 정한다.

## 식별자와 작업공간

Project는 업무 맥락, ExecutionTarget은 실행 장소, Workspace는 그 안의 디렉토리·worktree, Session은 대화와 선택한 작업공간, Run은 한 번의 요청 처리, Step은 모델 요청과 그에 따른 도구 실행 단위로 나눈다.

실행 위치에는 호스트 식별자, SSH 별칭, 컨테이너 식별자, 호스트 경로, 컨테이너 경로, Python·toolchain 환경을 기록한다. 파일 식별자는 경로 문자열뿐 아니라 실행 대상과 작업공간을 포함한다.

현재 세션의 기준 디렉토리를 전역 cwd로 구현하지 않는다. 각 도구 실행은 해석된 작업 디렉토리를 명시한다. 환경 변경은 이후 실행에 적용하며 이미 시작한 프로세스의 위치를 변경한 것처럼 표시하지 않는다.

동일 마운트를 사용하는 컨테이너·호스트 별칭은 공통 자원 식별자로 연결한다. 경로 매핑은 등록한 마운트와 실제 접근 검증을 기준으로 수행한다. 원격·로컬 사이에 파일을 조용히 동기화하지 않는다.

## 플러그인 계약

서비스 정의, 구현 제공자, 소비자 역할을 구분한다. 소비자는 구현 객체를 영구 보관하지 않고 교체 가능한 계약을 통해 접근한다. 리스너·타이머·파일 감시·등록은 플러그인의 정리 절차에 포함한다.

플러그인 manifest에는 이름·버전·계약 버전·의존성·구성 스키마·상태 형식·필요 capability를 표현하는 안을 검토한다. 장기 작업은 플러그인 내부의 메모리 핸들만으로 소유하지 않는다.

Core 구현 변경과 계약·영속 데이터 형식 변경은 별도 분류한다. 계약이 비호환이면 같은 hot reload 경로로 강행하지 않는다. Cordis 자체의 구현과 HMR 세부 동작은 고정할 버전의 소스·테스트로 확인한다.

자기 개선 제안에는 수정·검증·적용 범위와 실패 대응을 함께 기록한다. 한 번의 동의로 그 범위 안의 전체 절차를 진행하고 범위 변경에만 새 제안을 요청한다. 권한·승인 규칙·저장 형식 변경도 제안에서 식별할 수 있어야 한다.

## 실행 버전 전환

일반 변경은 새 작업에만 적용한다. 현재 작업 전환이 승인된 경우 후보 검증 → 안전 지점 대기 → 입력 admission 일시 정지 → 결과·상태 기록 → 상태 호환 확인 → 실행 소유권 이전 → 신규 입력 재개 순서를 제안한다.

이전 버전의 늦은 응답이 새 작업을 변경하지 못하도록 실행 버전과 소유권 세대를 검사한다. 파일 쓰기나 도구 결과의 중복 수용도 같은 실행 식별자로 확인한다. 단, 모든 외부 시스템에 exactly-once 실행을 보장할 수 있다고 가정하지 않는다.

안전 지점 이전에는 준비된 후보가 현재 작업의 외부 행동을 중복 수행하지 않는다. 상태 이전 대상은 직렬화 가능한 명시적 상태다. 임의의 JS 스택·클로저·진행 중 네트워크 요청을 이동시키지 않는다.

기본 120초의 대기 시간이 초과되면 현재 작업은 이전 버전에 남기고 새 버전은 이후 작업에 사용한다. 기존 버전이 담당하는 작업이 없을 때 자원을 정리한다. 플러그인 단위 교체와 실행 버전별 프로세스 분리는 각각 검증한다.

세션 이벤트 형식은 버전을 갖는다. 새 형식 기록 이후 이전 코드가 데이터를 읽을 수 있는지 확인하지 않고 롤백하지 않는다. 비호환 마이그레이션에는 별도 계획·보관본·실패 복구 절차가 필요하다.

## 도구 실행과 불확실한 결과

도구 실행에는 호출 ID, 대상, 인자, 승인 근거, 시작 상태, 외부 작업 ID, 결과 상태를 기록한다. 완료·실패·취소 외에 결과를 확인할 수 없는 상태를 표현한다.

예를 들어 PR 생성 요청 후 연결이 끊어지면 같은 요청을 바로 반복하지 않는다. 외부 식별자나 검색으로 결과를 확인하고 불명확하면 사용자에게 판단을 요청한다. 문서 저장·workload 생성·앱 설치에도 같은 원칙을 적용한다.

긴 작업의 취소 요청과 실제 프로세스 종료 확인을 구분한다. 작업 한도 도달은 새 행동을 차단하며 이미 시작한 작업의 처리는 해당 도구의 취소 계약을 따른다. GUI에는 남아 있는 외부 작업을 표시한다.

## 스케줄링과 자원

Agent 실행 슬롯 10개와 모델 요청 슬롯 3개를 별도로 관리한다. 부모가 자식을 기다리는 동안 실행 슬롯을 반납하고 자식 완료로 재개하는 상태를 둔다. 완료되지 않은 업무 수와 실제 실행 슬롯 사용량은 따로 표시한다.

프로젝트·세션 간 기아 상태를 방지하고 사용자가 우선순위를 바꿀 수 있게 한다. 화면 제어, 특정 Office 문서, ADB 기기, 동일 worktree, 컨테이너 수명 조작에 자원 소유권을 부여한다.

파일 편집 버퍼와 agent 쓰기는 기준 버전을 함께 관리한다. 미저장 사용자 내용은 보존하고, 변경이 겹치면 diff 적용을 요청한다. 겹치지 않는 변경은 병합을 시도한다. 열려 있지만 미저장 변경이 없는 파일은 변경 표시와 함께 자동 수정할 수 있다. 적용 직전에 버전을 다시 확인하고 agent 변경 복원과 사용자 undo를 구분한다.

## 모델과 Context

공통 이벤트 계약은 모델별 입력·도구 호출·스트림·사용량을 표현하되 지원하지 않는 기능을 지원하는 것처럼 정규화하지 않는다. 지원 capability와 요청 실패 원인을 UI에 노출한다.

역할·프로젝트·작업별 모델 선택을 해석하고 실제 호출한 endpoint·모델·설정·전환 이유를 기록한다. 자동 fallback은 사전에 지정한 대체 경로 안에서만 수행한다.

모델별 정확한 API 계약, 요청 취소, 스트림 중단 시 재시도, tool call 식별자, 이미지와 reasoning 관련 필드는 공식 문서와 테스트 endpoint로 검증한다. 프로토콜 이름만 같다고 모든 사내 endpoint의 동작이 같다고 가정하지 않는다.

원본 입력, 압축 결과, 기억 검색 결과, 전달한 context를 참조 가능하게 기록한다. 활성 기억과 오래된 원문을 구분하고 각 응답의 근거가 어떤 버전인지 추적한다.

## 저장과 검색

구조화된 로컬 메타데이터는 SQLite, 원문·첨부·큰 로그·context 기록은 별도 파일 저장소에 두고 참조한다. 키워드와 의미 검색을 함께 제공한다. FTS5의 한국어 검색 구성과 벡터 저장·검색 구현은 기술 검증 후 확정한다.

임베딩 모델 google/embeddinggemma-2를 로컬 Python worker에서 실행하고 설정에 모델 디렉토리를 지정한다. GPU 사용 가능 여부를 확인해 사용하며 CPU 실행도 지원한다. 모델 revision·전처리·task prompt·768차원·정규화 설정을 색인 버전에 연결한다. 질의와 문서가 호환되지 않는 색인을 섞지 않으며 설정 변경 시 필요한 재색인을 관리한다. 임베딩 불가 시 키워드 검색을 유지하고 의미 검색의 준비 상태를 표시한다.

첫 버전은 텍스트·코드·이미지를 768차원으로 색인하고 음성·영상은 이후 확장한다. Google의 공식 가이드에 따라 필요한 인코더만 로딩하는 구성을 검증한다. 사용자 질의를 대량 색인보다 우선 처리하고 배치 작업의 일시정지·재개를 제공한다. 모델 배포의 공표 수치만으로 사용자 PC에서의 지연·메모리 사용을 확정하지 않는다.

문서 이미지에는 원문 자산·버전·페이지·슬라이드 참조를 연결하고 텍스트 추출 결과와 같은 원문에서 왔음을 표현한다. DRM 문서의 미리보기·색인용 이미지 생성은 해당 Office 환경에서 가능한 동작으로 제한하고 미추출 상태를 표시한다.

원본 사본, 추출·요약·색인, 사용자 편집 기억, 작업 상태는 수명과 삭제 정책을 구분한다. 50GB 한도는 수집 저장 영역에 적용하고 다른 공간 사용량도 함께 표시한다.

Asset와 AssetVersion, ProjectAsset 관계, RunArtifact, EvidenceReference를 분리한다. 공유 모델의 새 버전은 기존 프로젝트의 선택 버전을 덮어쓰지 않는다. 출처 수정·삭제·접근 불가와 로컬 보관본의 상태를 각각 표시한다.

수동 전체·프로젝트 내보내기는 설정·기억·대화·작업 기록을 기본으로 하고 원문·첨부 포함은 선택한다. 원격 대용량 자산은 기본적으로 위치·식별 정보만 포함한다. 자동 정기 백업은 첫 버전 범위가 아니다. 원본 실행 기록 보존 기간과 내보내기 세부 형식은 별도 결정 사항이다.

자격증명은 운영체제 credential API를 도입하지 않고 설정 파일에서 필요한 파일 경로를 지정한다. 필요한 도구가 해당 파일을 읽고 설정에는 경로를 보관한다. 상대경로 해석 기준·파일 형식·내보내기 시 경로 재연결 동작은 설정 계약에 명시한다. 비밀파일 자체를 내보내기에 포함할지는 설정 내보내기와 구분해 결정한다.

## YAML 설정

사용자 기본 설정·프로젝트 설정·세션 선택값 순으로 유효 설정을 계산한다. 각 값에는 정의한 파일과 범위를 표시한다. UI와 직접 파일 편집은 같은 설정 원본을 사용한다. 파일 경로는 선언한 설정 파일을 기준으로 해석하는 방안을 검토하고 세션 cwd 변경에 따라 자격증명 경로가 바뀌지 않게 한다.

검증 실패 시 오류 위치를 보여주고 마지막 정상 설정을 유지한다. 변경 종류별로 즉시 적용·안전 지점 적용·재시작 필요를 구분한다. 단순 설정 우선순위가 미승인 권한 확대를 자동 허용하는 의미가 되지 않도록 기존 권한 계약을 적용한다.

## 대화 분기와 재개

분기는 원본 세션과 분기 지점의 기록 참조를 남긴 새 세션이다. 메시지 수정도 원본 기록을 덮어쓰지 않는다. 선택한 현재 작업공간의 파일 상태를 사용하며 과거 코드 상태 자동 복원은 첫 버전에서 제외한다.

분기한 대화에 포함된 과거 도구 결과는 당시 사실로 표시한다. 현재 파일·환경과 동일하다고 가정하지 않고 필요한 상태를 다시 확인한다. 과거 승인을 새 실행의 승인으로 자동 복사하지 않는다. 별도 worktree와 agent 변경 복원은 대화 시점 복원과 구분한다.

## 사내 네트워크

인증 없는 proxy와 사내 CA, 기존 네트워크 설정을 재사용한다. 모델 API, 패키지 설치, MCP, 자료 접근 등 네트워크 호출 경로별로 설정 적용 여부를 검증한다. TLS 검증을 끄는 방식으로 CA 연동을 대신하지 않는다. 자체 제작 실행 파일 실행은 가능하며 관리자 권한 요구는 미확인이다.

## 원격과 컨테이너

OpenSSH 클라이언트를 우선 사용해 기존 설정의 Host·Match·ProxyJump 등을 존중한다. 사용자의 설정을 임의 재작성하지 않는다. 실제 Windows OpenSSH 버전과 인증 방식은 검증한다.

원격 Python 실행부는 호스트와 컨테이너의 기존 인터프리터를 활용할 수 있게 설계한다. 제어 프로그램의 환경을 프로젝트 환경과 분리한다. 원격 uv 설치 여부와 실행부 의존성 배포는 검증 항목이다.

SSH 스트림과 독립적으로 유지할 장기 작업은 원격 작업 ID·로그·상태를 기록한다. 재접속은 상태 조회로 시작한다. 서버·컨테이너 재시작은 일반 SSH 끊김과 다른 장애로 처리한다.

컨테이너 템플릿은 이미지 identity·마운트·사용자·환경·포트·GPU·작업 디렉토리를 명시한다. 앱 생성 여부와 사용하는 세션·작업을 기록한다. 기본 자동 삭제는 하지 않는다. 기존 컨테이너를 worktree 지원 목적으로 조용히 재생성하지 않는다.

LSP와 빌드는 실제 toolchain 환경에서 실행한다. Python 인터프리터, clangd compilation database, Rust toolchain, JDK·Gradle 모델을 해당 대상에서 해석한다. 호스트 경로가 든 진단을 로컬 Windows 경로로 오인하지 않는다.

## NPU 변환과 실기기 평가

Windows의 로컬 agent가 변환·배포·평가 작업을 조율하고, USB가 연결된 Linux 실행 대상에서 기기를 제어한다. 세 SDK의 변환 도구는 Docker에서 실행하며 각각 이미지·SDK 버전·실행 위치·마운트를 등록한다.

PyTorch QAT 결과 → 원본 ONNX export → 필요한 경우 SDK별 레이어 수정본 → SDK별 변환 → 실행 산출물 → Linux USB 실기기 평가 → 비교 보고를 별도 작업 단계로 표현한다. Qualcomm QAIRT, Samsung Exynos enntools, MediaTek NeuroPilot의 입력·옵션·출력은 공통 계약 뒤의 별도 어댑터로 둔다. 기본적으로 같은 ONNX를 사용하되 수정본에는 원본과의 관계·변경 이유·변경 내역을 기록한다.

최종 출력 차이의 기준은 원본 ONNX다. 원본 실행 환경과 입력·전후처리·출력 대응 관계를 고정하는 평가 preset을 제안한다. 원본 ONNX와 파생 ONNX 간 비교를 보조 단계로 추가할 수 있지만 최종 기준을 파생 모델이나 PyTorch 출력으로 바꾸지 않는다.

변환 기록에는 입력 자산 버전, ONNX 관련 파일, 양자화 설정, SDK·어댑터 버전, 실행 환경, 명령·결과·출력 식별자를 연결하는 안을 제안한다. 재현에 필요한 SDK별 부가 자료는 명시적인 artifact로 기록한다.

평가 기록은 기기·펌웨어·런타임·입력 데이터·전후처리·반복 횟수·warmup·측정 조건을 연결하는 안을 제안한다. 지원되지 않는 지표를 0으로 대체하지 않고 미측정 상태로 표시한다. 동일 조건인지 확인하지 않은 결과를 단일 성능 순위로 제시하지 않는다.

기기는 Linux 실행 대상과 기기 식별자를 함께 사용해 구분한다. 보통 연결하는 한 기기를 기준으로 기기별 배타적 작업 소유권과 대기열을 두고 USB 단절 후 상태를 재확인한다. 여러 기기의 식별과 병렬 실행을 막는 전역 단일 기기 구조로 만들지는 않는다.

## 사내 변환과 평가 프로그램 등록

기존 스크립트·평가 프로그램은 사내 환경에서 에이전트에게 등록을 요청할 수 있게 한다. 등록 대상 경로를 읽고 실행 환경·입출력·명령·성공 판정·결과 파싱을 제안한 뒤, 사용자가 동의한 범위에서 등록과 시험 실행을 수행하는 흐름을 제안한다.

등록 단위에는 실행 대상·이미지·SDK 버전·인자 스키마·입력 artifact·출력 위치·완료 판정·로그 형식·지원 지표를 둔다. 기기 배포·실행·정리 절차와 중단·재시도 특성도 표현한다. Native runner·앱·SDK 평가 도구를 동일한 프로그램으로 가정하지 않는다.

기존 프로그램의 코드 수정과 프로그램을 호출하기 위한 등록은 구분한다. 시험 실행 전에는 등록만 된 상태로 표시하고, 실제 입력·출력 확인 후 검증된 등록 버전으로 활성화하는 안을 제안한다. 등록을 데이터·설정만으로 표현할 수 있으면 core를 수정하지 않고 적용한다. 새 해석 로직이 필요하면 별도 Cordis 어댑터로 구현한다.

현재 개발에서는 가상의 입출력 fixture로 등록·스케줄링·기록·실패 처리를 검증한다. 실제 SDK 변환·기기 평가는 사내 프로그램과 기기에 연결한 뒤 검증한다. Fixture 통과를 세 SDK의 실제 통합 성공으로 표시하지 않는다.

## Windows와 화면 제어

Office COM은 진행 중 작업과 연결된 문서 소유권을 갖는 worker에서 처리하는 안을 검증한다. DRM이 허용하는 읽기·저장·복구·미리보기 동작을 각각 시험한다. 원문 형식 보존이 평문 추출·캐시 허용을 뜻한다고 가정하지 않는다.

Browser는 기존 SSO Chrome 프로필을 기본으로 사용하고 에이전트 전용 프로필 선택도 지원한다. Chrome 확장프로그램 → Native Messaging Rust bridge → 상주 감독 프로세스 → Cordis browser 서비스 구조를 기본안으로 채택하고 사내 환경에서 검증한다. Bridge 수명과 agent·장기 작업 수명은 분리한다.

Native Messaging host 등록, 확장프로그램 식별자와 연결, 브리지 재시작·재접속을 검증한다. 구조화된 작은 제어 메시지를 사용하고 큰 문서·이미지는 분할 전송 등 크기 제한을 고려한 전달 경로를 설계한다. 대용량 파일을 임의로 단일 메시지에 넣지 않는다.

탭을 식별한 DOM·접근성 정보 조회와 입력 동작에 debugger API 등 필요한 확장 기능을 검토한다. API 사용 가능 여부, iframe·페이지 전환, DevTools 사용으로 인한 연결 해제, 사내 브라우저 정책을 실제 환경에서 확인한다. 웹 페이지에서 온 내용과 도구 실행 제어 메시지를 구분한다.

프로필·탭·작업 소유권은 별도로 관리한다. Agent는 작업별 새 탭을 만들고 기존 사용자 탭은 명시적 인계 후 사용한다. 사용자 제어 회수는 해당 작업을 일시정지한다. 화면 제어는 대기·허용·사용자 회수·인증 대기 상태를 가진다. 지정 시간 허용의 만료가 진행 중 입력에 미치는 처리도 정의한다.

사이트 연결에는 프로필, 시작 URL 또는 space, 포함·제외 경로, 수집 주기, 허용 동작을 기록한다. 범위를 벗어난 탐색은 연결 추가 제안으로 전환한다. 전체 탭 상시 수집은 하지 않는다. Agent의 일회성 조회 탭만 출처·결과 보관 후 정리하며 인계된 사용자 탭, 초안, 인증 대기, 사용자 고정 탭은 유지한다. 모든 탭 유지 설정도 제공한다.

정기 수집은 Chrome 종료 시 재연결까지 보류하고 브라우저를 자동 시작하지 않는 것을 기본값으로 한다. 인증 만료는 연결별 동일 원인 알림을 합치고 로그인 후 재개한다. 캐시 검색에는 마지막 수집 시각을 표시한다. 정기 수집과 사용자 요청의 브라우저 시작 정책은 별도 설정한다.

메신저는 접근성·UI 요소 기반 읽기를 먼저 검증한다. 기술적으로 가능하다는 것을 실제 사내 제품의 전체 대화 접근 보장으로 확대하지 않는다.

## 확장과 UI

AGENTS.md는 디렉토리 범위, SKILL.md는 사용 가능한 지침 패키지, MCP는 외부 도구 연결, Cordis는 서비스·실행 정책의 교체로 구분한다. 각각의 발견·실행·권한·버전 기록을 제공한다.

구조화된 도구 결과는 Rust의 표·폼·이미지·차트·diff·링크 컴포넌트에 매핑한다. 첫 버전에서 임의 JS UI 런타임을 추가하는 것은 합의하지 않았다. 새로운 Rust UI 동작은 앱 업데이트 경로를 따른다.
